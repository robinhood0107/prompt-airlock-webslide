Prompt Airlock 중간 발표

  • 공공기관 직원이 외부 LLM(인터넷으로 쓰는 대화형 언어모델 서비스)을 쓸 때, 질문 속 개인정보가 밖으로 나가지 않게 막는 프로그램
  • 10월 결과: 질문 입력부터 답 받기까지 실제로 동작하는 첫 버전(MVP), 감사 기록과 운영 기능

발표 순서: 문제 → 용어 → 기존 도구 → 차이 → 처리 순서 → 시연 → 검증 결과 → 다음 계획

문제: 질문에 개인정보가 섞여 있음

"한빛시청 김민준 주무관에게 010-2345-6789 로 회의 일정을 알려 주는 안내문을 써 줘"

  • 이 질문을 외부 LLM 에 그대로 보내면 이름·소속·전화번호가 외부 회사 서버에 저장될 수 있음
  • 그렇다고 개인정보를 지우면 "누구에게, 어디로 연락하라는지" 알 수 없어 쓸모 있는 답을 받기 어려움
  • 공공기관 보안 지침도 외부 LLM 에 보내는 입력과 받은 답에서 민감정보를 찾아 막도록 요구함

근거: 국가정보원 외부 언어모델 활용 보안 가이드라인(2023), 국가망 보안체계(N2SF)

해결 방향: 가명으로 바꿔 보내고, 답에서 되돌리기

  1. 보내기 전: 개인정보 자리를 찾아 임의 문자열(가명)로 바꿈
    김민준 → ⟦PERSON_PYZHWD8MSY⟧, 010-2345-6789 → ⟦KOREAN_PHONE_N84Q9DY2F5⟧
  2. 외부 LLM 은 가명이 든 질문만 받고, 답에도 같은 가명을 넣어 돌려줌
  3. 답을 받으면 가명을 원래 값으로 다시 바꿔 직원에게 전달

가명과 원래 값의 짝은 기관 안의 별도 프로그램(Vault)에만 저장 → 외부에서는 가명만 보고 원래 값을 알 수 없음

용어 정리

provider외부 LLM 을 인터넷(API)으로 빌려주는 회사. 기관 밖에 있으므로 개인정보를 보내면 안 되는 곳.
게이트웨이기관 직원의 앱과 provider 사이에서 요청을 대신 전달하는 서버. 모든 질문이 여기를 지나가므로 한곳에서 검사 가능.
탐지 · NER탐지: 질문에서 개인정보 위치를 찾는 일. NER: 문장 속 사람·기관 이름을 찾도록 학습된 모델(전화번호처럼 모양이 정해지지 않은 이름을 찾을 때 사용).
token(가명)원래 값 대신 넣는 임의 문자열. 요청마다 새로 만들어 다른 요청에서는 쓸 수 없음.
Vault가명과 원래 값의 짝을 보관하는 별도 프로그램. 게이트웨이와 따로 실행돼 한쪽이 뚫려도 피해를 줄임.
fail closed검사 도구가 고장 나거나 결과가 불확실하면 "보내지 않는 쪽"을 택하는 원칙.

기존 도구 ① LiteLLM

  • 여러 회사의 provider 를 같은 요청 형식으로 쓸 수 있게 해 주는 공개 프록시(중간 전달 서버)
  • 가드레일: 요청을 보내기 전(pre_call)과 답을 받은 뒤(post_call)에 검사 프로그램을 끼우는 기능
  • 개인정보 가리기: 검사 프로그램으로 Presidio 를 별도 서버로 띄워 호출
  • output_parse_pii 옵션을 켜면 답 속의 자리표시자(가린 자리)를 원래 값으로 되돌림

정리: 범용 중계 서버 + 필요하면 개인정보 검사기를 붙이는 구조 · 출처: LiteLLM 공식 문서 Guardrails › PII Masking (Presidio)

기존 도구 ② Presidio

  • Microsoft 가 공개한 개인정보 탐지·가리기 도구
  • Analyzer(찾기): 정규식(글자 모양 규칙), 체크섬(번호 검산), NER 로 개인정보 위치를 찾음
  • Anonymizer(바꾸기): 찾은 자리를 다른 글자로 치환, 별표로 가리기, 해시, 암호화 등으로 처리
  • LiteLLM 연동의 기본 언어는 영어. 주민등록번호, 국내 계좌·전화번호 같은 한국 형식은 사용자가 직접 규칙을 만들어 넣어야 함

이 프로젝트도 "찾기 → 바꾸기" 두 단계 구조를 그대로 따름. 다른 점은 다음 장

항목LiteLLM + PresidioPrompt Airlock

가명 짝 보관프록시 프로그램 안별도 Vault 프로그램(요청이 끝나면 삭제)

처리 순서(8단계)

1~5단계를 모두 통과한 질문만 provider 로 전송.

어느 단계든 실패하면 그 자리에서 거절.

입구

  1. 암호화 연결(TLS)과 등록된 앱인지 확인
  2. 문서 등급 확인: C·S 면 거절

개인정보
보호

  1. 개인정보 찾기(규칙 + 한국어 NER)
  2. Vault 에서 가명 받아 바꾸기
  3. 바꾼 질문에 원문이 남았는지 한 번 더 찾기

외부 LLM
및 응답

  1. provider 로 전송
  2. 받은 답 검사(위험한 내용·링크)
  3. 같은 요청의 가명만 원래 값으로 되돌림

가명이 오가는 과정

  • 밖으로 나가는 질문에는 가명만 들어감
  • 답이 오면 이번 요청에서 만든 가명만 원래 값으로 되돌림
  • 한 글자라도 바뀐 가명은 비슷해 보여도 되돌리지 않음 → 다른 사람의 값이 잘못 들어가는 사고 방지
  • 답의 링크 주소 안에 가명이 있으면 답 전체를 거절 → 링크를 누르는 순간 원래 값이 외부 사이트로 전달되는 것을 막음

검사를 건너뛸 수 없게 만든 방법

  • 타입: 프로그램에서 값의 종류를 구분하는 표시. 종류가 맞지 않으면 컴파일(프로그램 만들기) 단계에서 오류
  • 질문은 RawPrompt(원본) → PolicyChecked(등급 확인) → Protected(가명 처리) → VerifiedPrompt(최종 검사 통과) 순서로만 바뀜
  • provider 로 보낼 요청은 VerifiedPrompt 로만 만들 수 있음 → 검사를 건너뛴 코드는 아예 만들어지지 않음
  • Vault·탐지 모델이 고장 나도 "검사 없이 보내기" 경로가 없음

고장 나면 보내지 않기(fail closed)

  • NER 모델이 멈춤 → 개인정보를 다 찾았는지 알 수 없으므로 거절
  • Vault 가 멈춤 → 가명을 받을 수 없으므로 거절
  • 가명으로 바꾼 뒤에도 원문이 남음 → 거절
  • 세 경우 모두 provider 호출 0번(시험으로 확인)

기록과 운영

  • 감사 기록: 요청마다 언제, 어느 앱이, 어떤 결과였는지 로컬 파일에 한 줄씩 저장(원래 값은 저장하지 않음)
  • 외부 전송 이력: 실제로 밖에 보낸 가명 질문과 받은 답을 1년 이상 보관(거절된 요청은 결과만 기록)
  • 변조 확인: 각 줄에 앞 줄의 해시(내용 요약값)를 함께 저장 → 중간 줄을 고치거나 지우면 검증에서 발견
  • 운영: 기록 열람·검증은 서버에서만 명령어로, provider 열쇠(API key)는 암호화된 파일로만 보관

시연: 실제로 실행해 보낸 질문 6개

  1. S 등급 문서 → 403(거절), 밖으로 나간 것 없음
  2. 주민등록번호·카드번호 → 400(거절), 어떤 종류였는지만 알려 줌
  3. 이름·전화·이메일 → 가명으로 나가고, 받은 답에서 원래 값으로 복원
  4. LLM 이 가명을 링크 주소에 넣음 → 답 전체 거절
  5. base64(문자를 다른 글자로 바꿔 숨기는 방식)로 감춘 주민등록번호 → 풀어서 찾아 거절
  6. LLM 이 가명 한 글자를 바꿈 → 되돌리지 않고 거절

게이트웨이(127.0.0.1:18443)와 시험용 provider(19443)를 실제로 실행해 기록한 결과. 왼쪽: 보낸 질문과 받은 결과, 오른쪽: provider 가 실제로 받은 내용
